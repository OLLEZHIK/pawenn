# Протокол совместной работы: Antigravity + Claude Code

Этот файл описывает, как несколько ИИ-агентов работают над проектом
без пересечения друг с другом. Прочитайте его перед началом работы —
все агенты (Antigravity, Claude Code CLI локально, Claude Code в
облаке) должны следовать этому протоколу.

**Агенты и роли:**
- **Claude Code (облако)** — оркестратор и ревьюер. Ставит задачи,
  проверяет PR и готовит их к мержу владельцу, отвечает за правила для
  агентов. Сам в `main` не мержит (раздел «Мерж — только владелец»). Не пишет код
  сам, кроме файлов протокола (`AGENTS.md`, `docs/`, `tasks/`) и
  скриптов проверки данных (`website/scripts/check-city.ts`,
  `verify-city.ts`, `evidence.ts`).
- **Claude Code (облако), «правая рука»** — отдельная облачная сессия,
  работает напрямую с владельцем, пишет и код приложения по его
  запросам (подробнее — раздел «Роли»).
- **Claude Code (облако), «левая рука»** — отдельная облачная сессия,
  личный исполнитель владельца: делает ровно то, что владелец говорит
  ему напрямую в чате. Имеет приоритет выше оркетратора на уровне правой руки  Задачи из `tasks/` сам не берёт.
- **Claude Code (облако), «дизайнер»** — отдельная облачная сессия
  для редизайна сайта, работает напрямую с владельцем. **Ничего не
  мержит и не выкатывает без явного одобрения владельца**; его PR не
  мержит никто другой. Бриф — `docs/roles/designer.md`.
- **Antigravity (локально)** — исполнитель.
- **Antigravity (Mac)** — ещё один исполнитель, та же роль, своя
  очередь задач (`mac-*.md`).
- **Antigravity (Mac 2)** — Antigravity на Mac со вторым аккаунтом,
  та же роль, своя очередь задач (`mac2-*.md`).
- **Claude Code CLI (локально)** — второй исполнитель, работает
  параллельно с Antigravity на независимых задачах.
- **Claude Code CLI (Mac)** — ещё один исполнитель на Mac владельца,
  своя очередь задач (`cmac-*.md`).
- **Antigravity (ПК N)** — исполнители в Docker-контейнерах `agyN` на
  Windows-ПК владельца, пронумерованы (`ПК 1`, `ПК 2`, …); очередь
  каждого — `pcN-*.md`.
- **Claude Code CLI (ПК, диспетчер)** — на том же ПК: только надзор —
  раздаёт задачи `pcN-*` контейнерам, следит за их лимитами и
  перенаправляет задачи; сам задачи не делает (раздел «Роли»).

**Сейчас работают Antigravity (Mac 2), Claude Code CLI (Mac)
(владелец, 2026-09-29) и Antigravity (ПК 1) через диспетчера на ПК
(владелец, 2026-09-30).** Задачи ставятся только им (`mac2-`, `cmac-`,
`pc1-`).
Antigravity (Mac), IDE, Desktop и локальный CLI на паузе: задачи
Antigravity (Mac) переданы Mac 2 (его ветка `mac/warszawa-descriptions`
продолжается в `mac2/…`), открытые PR остальных ждут их возвращения
(PR #186 — сводки Кошице, Desktop).

**Мерж в `main` делает только владелец (владелец, 2026-09-30).** Все
агенты, включая облачные сессии Claude Code, только предлагают
изменения через PR; оркестратор проверяет PR и пишет в нём вердикт
«Готово к мержу», мержит владелец. Это правило главнее любого места
ниже, где сказано «мержит», «мёржит» или «после этого мержить»: там
теперь читать «готовит к мержу владельцу». Критическая инфраструктура
(GitHub, секреты, база, хостинг, автозапуск агентов) — только с прямого
подтверждения владельца, см. раздел «Критическая инфраструктура».

## Принцип автономности

Владелец проекта явно попросил работать автономно: **не задавать
уточняющих вопросов по вопросам продукта/дизайна/названий/масштаба
задачи, если решение можно принять самостоятельно** — принять решение,
кратко зафиксировать причину прямо там, где это уместно (PR, коммит,
этот файл), и продолжить работу, а не останавливаться в ожидании
ответа. Это касается Claude Code в первую очередь, но применимо и к
Antigravity в части задач вроде «что включить в объём», «как назвать
файл/категорию» и т.п.

**Это не отменяет** отдельное правило про данные (см. ниже: «не
выдумывать факты о салонах/клиниках/ценах»). Разница простая:
- **Факт о реальном мире** (адрес, цена, название реального салона) —
  нельзя придумывать. Не нашёл — оставь пустым, поясни в notes.
- **Решение о продукте** (как назвать категорию, какой домен выбрать
  из свободных вариантов, как разбить задачу на подзадачи) — можно и
  нужно решать самому, не спрашивая.

Это же касается **выбора, за какую задачу браться**, если подходящих
несколько: не спрашивать «какую делать», а выбрать самому по понятному
приоритету (см. «Распределение задач между агентами», шаг 5) и сразу
начать работу.

Останавливаться и спрашивать владельца стоит только для решений,
которые: (а) стоят реальных денег без возможности отменить (покупка
домена, платная подписка), (б) юридически значимы (тексты политик,
статус оператора, налоги), или (в) необратимо меняют архитектуру
проекта уже после того, как на неё что-то построено, или (г) касаются
критической инфраструктуры (раздел «Критическая инфраструктура» ниже).
Во всех остальных случаях — решать и делать.

## Роли

**Antigravity (IDE и/или Desktop/Hub)** — исполнитель ("worker").
- Обязательно открыта на локальной папке проекта (клон репозитория)
  на компьютере владельца проекта — иначе IDE в принципе не может
  работать. Это не опция, а требование к запуску.
- Работает локально, на компьютере владельца проекта.
- Имеет прямой доступ к файловой системе репозитория и к GitHub.
- Пишет код, тесты, исправления по поставленной задаче.
- Никогда не решает архитектурные вопросы самостоятельно, если задача
  их не описывает явно — в таком случае останавливается и описывает
  вопрос в PR, а не гадает.

**Antigravity (Mac)** — третий исполнитель ("worker"), добавлен
2026-09-25. Отдельная установка Antigravity на Mac владельца, со своим
клоном репозитория. Роль и правила — те же, что у Antigravity выше
(данные, контент, исследования; не фронтенд). Свой префикс задач
`mac-*.md` и свои ветки `mac/…`, чтобы не пересекаться с Antigravity
IDE/Desktop: у каждой установки своя очередь задач, и две установки
никогда не берут один и тот же файл задачи.

**Antigravity (Mac 2)** — исполнитель ("worker"), добавлен 2026-09-29.
Antigravity на Mac владельца со вторым аккаунтом — отдельная квота и
отдельные сессии, работает параллельно с Antigravity (Mac). Роль и
правила — те же, что у Antigravity (данные, контент, исследования; не
фронтенд). Свой префикс задач `mac2-*.md` и свои ветки `mac2/…`; своя
папка-клон репозитория, не общая с Antigravity (Mac), — иначе две
сессии перепишут друг другу рабочие файлы.

**Antigravity (ПК N)** — исполнители ("worker"), добавлены 2026-09-30.
Antigravity CLI (`agy`) в Docker-контейнерах `agy1`, `agy2`, … на
Windows-ПК владельца; у каждого свой клон, свой аккаунт Google и свой
токен GitHub-бота `wernir` (коллаборатор: пушит свои ветки и открывает
PR, мержить не может). Роль и правила — как у Antigravity (данные,
контент, исследования; без Google Maps и фронтенда). Номер контейнера =
номер агента: префикс задач `pcN-*.md`, ветки `pcN/…`, в `.git/agent` —
`Antigravity (ПК N)`. Задачу берут **только по поручению диспетчера** —
сами по `tasks/` не выбирают, чтобы два контейнера не взяли одно и то
же. Что каждый умеет хорошо и плохо — `docs/pc-agents/capabilities.md`.

**Claude Code CLI (ПК, диспетчер)** — добавлен 2026-09-30. Claude Code
CLI на том же ПК, свой клон (`D:\docker\shop`), в `.git/agent` —
`Claude Code CLI (ПК, диспетчер)`.
- По команде владельца смотрит задачи `pcN-*.md` в свежем `main` и
  передаёт каждую в её контейнер: `docker exec agyN …` с текстом
  поручения (длинный текст — файлом, не через кавычки PowerShell).
- Кому что давать — по `docs/pc-agents/capabilities.md`: ❔ — только
  пилот, ❌ — не давать, а сказать владельцу.
- Одна задача — одному контейнеру; пока контейнер занят, новую ему не
  давать.
- Сам задачи из `tasks/` не делает и код не пишет; после запуска —
  отчёт владельцу: кому что дал, ссылки на PR, где застряло. Наблюдения
  о среде — в `capabilities.md` через PR.
- Создание и удаление контейнеров, токены, запуск по расписанию —
  критическая инфраструктура, только с прямого подтверждения владельца.
- **Только надзор, ресурс экономить (владелец, 2026-10-01).** Ни карту,
  ни сайты сам не проходит: всё делают Antigravity. Его работа — очередь
  задач, лимиты агентов (агент упёрся в лимит — его задача уходит
  свободному агенту), перекрёстные проверки карты и отчёт владельцу. Как —
  `docs/pc-agents/dispatcher.md`; конвейер города —
  `docs/pc-agents/pipeline.md`.
- **Взаимная проверка (владелец, 2026-10-01):** каждый PR агента на ПК
  сначала проверяет другой Antigravity («Проверка напарника» в PR), и
  только потом облачный проверяющий (`docs/pc-agents/pipeline.md`).

**Claude Code CLI (локальный)** — второй исполнитель ("worker").
- Запущен локально на компьютере владельца проекта, в клоне
  репозитория (`claude` в терминале внутри папки проекта).
- Имеет прямой доступ к файловой системе репозитория, к GitHub и (в
  отличие от облачного Claude Code) может ставить и использовать MCP
  и плагины локально — например, Playwright MCP для проверки
  реального запущенного сайта, а не только диффа кода.
- Работает по тому же протоколу, что и Antigravity: свой префикс
  задач, своя ветка, PR, ревью от облачного Claude Code.
- Правила и рабочий цикл — те же, что для Antigravity (см. разделы
  «Рабочий цикл» и «Правила, обязательные для исполнителей» ниже).
- **Права — как у Antigravity (владелец, 2026-09-28, тестовый период):**
  CLI берёт и задачи на данные, контент, исследования и скрипты, а не
  только фронтенд. Его задачи — `cli-*.md`, ветки `cli/…`, PR и ревью —
  как у Antigravity; те же правила качества (`docs/playbooks/quality.md`)
  и те же запреты (не мёржить самому, не трогать чужие задачи и ветки,
  не пушить в `main`). Начинаем с небольших задач; по их итогам владелец
  решит, расширять ли объём.

**Claude Code CLI (Mac)** — исполнитель ("worker"), добавлен
2026-09-29. Отдельная установка Claude Code CLI на Mac владельца, со
своим клоном репозитория. Роль, права и правила — те же, что у Claude
Code CLI выше (данные, контент, исследования, скрипты и фронтенд; те же
запреты). Свой префикс задач `cmac-*.md` и свои ветки `cmac/…` — чтобы
не пересекаться ни с CLI (`cli-`), ни с Antigravity (Mac) (`mac-`).
Для задач с Google Maps нужен настоящий браузер: MCP Playwright
(`claude mcp add playwright npx @playwright/mcp@latest`) — без него
карточки Maps не открываются. С 2026-09-29 работа с Google Maps — только
у CLI (раздел «Распределение задач», «Специализация»); то же относится к
Claude Code CLI (локальному).

**Claude Code (облачный)** — оркестратор и ревьюер ("reviewer").
- Работает в отдельной облачной сессии, доступа к локальной папке
  на компьютере не имеет — видит только то, что запушено в GitHub.
- Ставит задачи (или получает их от владельца проекта), проверяет
  результат обоих исполнителей, оставляет замечания, отмечает готовые PR
  вердиктом «Готово к мержу» — мержит владелец.
- Не трогает ветки исполнителей напрямую, кроме как через комментарии
  в PR (или тривиальные правки, см. «Правила, обязательные для
  Claude Code» ниже) — основная правка кода остаётся за исполнителем.
- **Отвечает за постановку задач, проверку и улучшение правил для
  агентов (владелец, 2026-09-28).** Каждую ошибку, найденную при
  ревью, в тот же день превращает в правило (`docs/playbooks/quality.md`,
  плейбук работы) и, где можно, в проверку скриптом (`check-city`,
  `verify-city`) — скрипты проверки данных входят в правила, это не код
  сайта. Задачи ставит по шаблону `docs/playbooks/task-template.md`:
  маленькие партии, доказательства, право на честный пробел.

**Claude Code (облачный, «правая рука» владельца)** — отдельная
облачная сессия, которая работает напрямую с владельцем (решение
владельца, 2026-09-23). В отличие от оркестратора, пишет и код
приложения по прямым запросам владельца: ветки `claude/*`, всё через
PR. Локально поднимает сайт (Postgres + Playwright) и проверяет
результат визуально. Задачи на сбор данных не делает сам, а оформляет
как `tasks/antigravity-*.md`: владелец передаёт их Antigravity через
оркестратора.

**Claude Code (облачный), «левая рука»** — исполнитель прямых
поручений владельца ("owner's hand").
- Отдельная облачная сессия Claude Code — не оркестратор и не
  «правая рука». Локальной папки владельца не видит, работает с тем,
  что запушено в GitHub.
- Работает **только по прямым указаниям владельца в своём чате**. Не
  проходит самоопределение по `tasks/` (шаги 1-6 ниже к нему не
  относятся), не берёт чужие задачи и не отвечает на «проверь задачу»
  выбором файла из `tasks/`.
- Не ревьюит и не мержит чужие PR и не переносит файлы в
  `tasks/done/`, если владелец прямо не поручил этого — это работа
  оркестратора. Свои PR тоже не мержит сам без указания владельца —
  их проверяет оркестратор по обычному циклу.
- Объём работы определяет поручение владельца: это может быть и код
  приложения, и данные, и файлы протокола. Прямое указание владельца
  важнее правил распределения задач по префиксам (в том числе правила
  «фронтенд только за CLI») — но если поручение визуальное и «левая
  рука» не проверила результат в браузере, она пишет об этом в PR,
  чтобы проверку сделал CLI, «правая рука» или владелец.
- Не трогает ветки `antigravity/*`, `cli/*` и файлы задач, которые
  уже взяты другим исполнителем (есть ветка/PR), без прямого указания
  владельца.
- Как отличить от оркестратора и «правой руки»: ветки у всех
  `claude/<автоимя>`
  (имя генерирует среда), поэтому PR «левой руки» начинаются с
  префикса `[левая рука]` в заголовке, а в описании есть строка
  «Исполнитель: Claude Code (облачный, «левая рука») по прямому
  указанию владельца».

**Claude Code (облачный), «дизайнер»** — редизайн сайта (решение
владельца, 2026-09-26). Полный бриф: концепция, решения, порядок
работы — `docs/roles/designer.md`.
- Работает по прямым указаниям владельца в своём чате, задачи из
  `tasks/` не берёт. Ветки `claude/<автоимя>`, PR с префиксом
  `[дизайнер]` в заголовке.
- **Никогда не мержит PR в `main` и не выкатывает версию сайта, пока
  владелец в его чате явно не одобрил именно эту версию.** До этого
  PR — черновик, владелец смотрит Vercel preview.
- **PR «дизайнера» никто другой не мержит** (оркестратор, «правая» и
  «левая рука» в том числе) — только сам «дизайнер» после явного
  одобрения владельца.
- Правило «фронтенд только за CLI» на него не распространяется: это
  прямое поручение владельца, результат дизайнер проверяет сам в
  браузере (Playwright).

Все агенты подключены к одному репозиторию на GitHub (см. раздел
«Проект» выше). Единственная точка синхронизации между ними — GitHub
(ветки, коммиты, Pull Request'ы), а не файловая система напрямую.

- Ветки Antigravity (Mac): `mac/<короткое-описание-задачи>`.
- Ветки Antigravity (Mac 2): `mac2/<короткое-описание-задачи>`.
- Ветки Claude Code CLI (локальный, исполнитель): `cli/<короткое-описание-задачи>`.
- Ветки Claude Code CLI (Mac): `cmac/<короткое-описание-задачи>`.
- Ветки Antigravity (ПК N): `pcN/<короткое-описание-задачи>` (например,
  `pc1/presov-01-vet`).
- Ветки Claude Code (облачный, оркестратор): `claude/<автогенерируемое-имя>` —
  только для файлов протокола (`AGENTS.md`, `docs/`, `tasks/`) и скриптов
  проверки данных, не для кода приложения.
- **Ветка города `city/<slug>` (владелец, 2026-09-28)** — в ней
  собирается новый город партиями (`docs/playbooks/add-city.md`,
  «Партии»). Создаёт исполнитель партии 0 от свежего `main`; прямых
  пушей в неё нет — только PR партий, их мёржит владелец после ревью
  оркестратора. В `main`
  город уходит одним PR от оркестратора, когда смёржены все партии.
- Ветки Claude Code (облачный, «левая рука»): тоже
  `claude/<автогенерируемое-имя>`, но с любыми файлами в рамках
  поручения владельца; PR помечаются префиксом `[левая рука]` (см.
  раздел «Роли»).
- Ветки Claude Code (облачный, «дизайнер»): `claude/<автогенерируемое-имя>`,
  PR с префиксом `[дизайнер]`; мерж — только после явного одобрения
  владельца (см. раздел «Роли»).
- Прямые пуши в `main` запрещены всем агентам. Всё идёт через PR.
- Одна ветка = одна задача. Не смешивать несвязанные изменения в одном PR.
- **Не пушить каждый шаг (владелец, 2026-09-27).** Каждый пуш в ветку и
  каждый мердж, где меняется `website/` или `data/`, запускает сборку
  Vercel, а у бесплатного тарифа дневной лимит сборок (при превышении —
  «Deployment rate limited — retry in 24 hours», сайт не выкладывается).
  Поэтому: коммитить локально сколько угодно, пушить работу целиком,
  когда она проверена; внутренние изменения (скрипты, служебные поля,
  то, чего посетитель не видит) не мёржить по одному, а собирать и
  выкатывать вместе с ближайшим видимым изменением. Правки только в
  `docs/`, `tasks/`, `AGENTS.md` сборку не запускают — их можно пушить
  сразу.

## Распределение задач между агентами

Все задачи лежат в папке `tasks/`. Чтобы не приходилось каждый раз
писать длинную инструкцию, у задач есть соглашение об именовании и
самоопределении исполнителя:

- **Имя файла начинается с префикса исполнителя:**
  - `ide-*.md` — задача для **Antigravity IDE**;
  - `mac-*.md` — задача для **Antigravity (Mac)**;
  - `mac2-*.md` — задача для **Antigravity (Mac 2)**, второй аккаунт;
  - `antigravity-*.md` — задача для **Antigravity (Desktop / Hub)**;
  - `cli-*.md` — задача для **Claude Code CLI (локальный)**;
  - `cmac-*.md` — задача для **Claude Code CLI (Mac)**;
  - `pcN-*.md` (`pc1-`, `pc2-`, …) — задача для **Antigravity (ПК N)**,
    передаёт диспетчер;
  - `claude-*.md` — задача для **Claude Code (облачный)**, обычно
    только файлы протокола, а не код приложения.
- **Внутри файла первая строка после заголовка** — поле
  `**Исполнитель:** <имя>`, дублирует префикс явно.

**Весь фронтенд/внешний вид сайта (`website/app/**`, `website/components/**`,
вёрстка, страницы, шапка/футер, всё, что влияет на то, как сайт
выглядит и ведёт себя в браузере) — закреплено только за Claude Code
CLI, никогда за Antigravity.** Причина: только у Claude Code CLI есть
возможность локально поднять сайт и реально визуально проверить
результат (например, через Playwright MCP, см. раздел «Роли» выше) —
у Antigravity такой возможности нет, и визуальные задачи без способа
их проверить выходят криво. Antigravity получает данные, контент,
дизайн-концепты (SVG и т.п.), исследования — но не задачи вида
`*-build-*-pages.md`/`*-shell-and-static-pages.md` и подобные, где
результат — работающий визуально интерфейс. Если по ошибке такая
задача оказалась с префиксом `antigravity-`/`ide-`/`mac-` — переименовать её
обратно на `cli-` при первой же возможности, а не оставлять как есть.

**Специализация: Google Maps — только Claude Code CLI, сайты мест —
Antigravity (владелец, 2026-09-29).**
- **CLI (`cli-`, `cmac-`)** — всё, что берётся с Google Maps: список
  мест нового города с данными карточек (партия 0, «проход Maps»),
  ссылки Maps, рейтинг и число оценок, часы с карточки, ленты отзывов и
  сводки (`review-insights`).
- **Antigravity (все установки)** Google Maps не открывает. Его задачи —
  то, что место пишет о себе само: сайт и соцсети (тексты, цены, факты,
  языки, специальности, логотипы, часы с сайта), и исправления по
  спискам `check-city`.
- **Новый город — два прохода.** Партия 0 — CLI: `candidates.csv` с
  данными карточки каждого места (`docs/playbooks/add-city.md`,
  «Партии»). Партии мест — Antigravity по сайтам: столбцы Maps копирует
  из `candidates.csv` без изменений; `check-city` сверяет, и ссылка,
  рейтинг или часы «с карточки», которых нет в списке, не пройдут
  ворота.
- Место без сайта и соцсетей Antigravity описывает только тем, что уже
  есть в строке (категория, название, адрес), — без деталей «с
  карточки».
- Браузер CLI для Maps — Playwright MCP с выполненным входом в Google
  (отдельный аккаунт, не основной): без входа Maps в ЕС урезан, отзывов
  не видно (проверка — «Подготовка» в `docs/playbooks/review-insights.md`).
- Начатое до 2026-09-29 доделывает тот, кто начал: Краков — CLI (Mac)
  целиком, сводки Кошице (PR #186) — Antigravity (Desktop).

- **Antigravity, сдавший экзамен по Maps, делает проход Maps
  (владелец, 2026-10-01).** Экзамен — вслепую против данных CLI, скриптом
  (`docs/pc-agents/maps-exam.md`), два PASS подряд в разных категориях.
  Сдали: Antigravity (Mac 2). Контейнеры ПК — после своего экзамена в
  Docker (нужен Chromium в образе). Каждый кусок карты — перекрёстная
  проверка: другой агент вслепую собирает 5 из 10 мест, `maps-exam.ts`
  сравнивает (`docs/pc-agents/pipeline.md`). **Отзывы и сводки
  (`review-insights`) — по-прежнему только CLI**, пока Antigravity не
  сдаст экзамен по отзывам (`docs/pc-agents/reviews-exam.md`). Для остальных агентов правило выше в
  силе.

Почему: у CLI (Mac) в Кракове сошлись все 481 ссылка Maps и найдены
137 цитат из 137 (PR #195, #200). У Antigravity Maps открывается в
урезанном виде без вкладки отзывов (PR #197), а где данных не видно,
появляются догадки: улицы у 9 из 11 мест без сайта (PR #199). Если
установка Antigravity захочет вернуть себе Maps — пилот на 10 мест с
проверкой каждого значения, решение за владельцем.

**Не давать Claude Code CLI задачи, которые может сделать Antigravity
(правило владельца, 2026-09-21; на тестовый период с 2026-09-28
приостановлено — CLI получает и задачи уровня Antigravity, см. раздел
«Роли»; с 2026-09-29 работа с Google Maps — всегда CLI, см.
«Специализация» выше).** CLI — ограниченный ресурс, его
использование резервируется под (а) фронтенд/визуальную работу (см.
правило выше) и (б) другие важные/высокоуязвимые задачи — например,
операции с реальными продакшен-секретами и миграциями БД
(`prisma migrate` против настоящей базы), архитектурные решения,
задачи, от которых напрямую зависят несколько других задач. Всё
остальное — сбор/обработка данных, контент, скрипты, исследования,
CSV/бэкенд-работа без визуальной проверки — по умолчанию задача для
Antigravity, а не CLI, даже если раньше подобное давали CLI. Не
переносить задачу с CLI на Antigravity **посреди работы** — если CLI
уже начал (ветка создана, или CLI сам сообщил, что взялся за задачу,
даже без ветки) — дать закончить, правило действует для *новых*
задач и назначений, а не ради отзыва уже начатого прогресса.

**Задачи на сбор данных о заведениях ставятся по городам, а не по
отдельным полям (правило владельца, 2026-09-25).** Что должно быть в
карточке каждого заведения и на каких языках — единый список в
`docs/card-spec.md`. Задача на город (`docs/playbooks/add-city.md`)
собирает сразу все поля оттуда, чтобы каждый агент просто брал свой
город. Новые задачи «на одно поле для всех городов» не ставить; если в
стандарт добавляется поле — сначала правится `docs/card-spec.md`.

**Как агент должен себя вести, когда человек просто пишет «проверь
задачу» / «выполни задачу» без указания конкретного файла.** Владелец
пишет агентам только эти два слова (владелец, 2026-09-29): всё остальное
агент находит сам — кто он, что делать и в каком порядке.

1. **Кто ты** — файл `.git/agent` в своём клоне: `cat .git/agent`. Он не
   в git, у каждой установки свой. Нет файла — спросить владельца один
   раз и записать ответ, например `echo "Antigravity (Mac 2)" > .git/agent`.
   Имена: Antigravity IDE / Antigravity Desktop / Antigravity (Mac) /
   Antigravity (Mac 2) / Claude Code CLI / Claude Code CLI (Mac) /
   Antigravity (ПК N) / Claude Code CLI (ПК, диспетчер).
2. Открыть папку `tasks/` **в свежем `main`** и найти файлы со своим
   префиксом: `git fetch origin && git checkout main && git pull`, или,
   если продолжаешь свою ветку, — `git pull origin main` в неё до того,
   как читать задачу. **Файл задачи в старой ветке может быть
   устаревшим**: ревью, ответы и новые пункты проверяющий пишет в `main`
   (урок 2026-09-29: Antigravity Mac продолжал ветку вчерашнего дня и не
   увидел ревью, дописанное в задачу утром).
3. **Что делать — строка «Сейчас:»** в начале каждого своего файла
   задачи. Её обновляет проверяющий после каждого ревью: там следующее
   действие — исправить по «Ревью N», открыть PR, следующая партия,
   ждать. Порядок по своим задачам:
   1. задача, где «Сейчас:» велит исправить или доделать, — первой
      (ревью важнее новой работы);
   2. своя ветка без PR — доделать и открыть PR (коммит — не сдача);
   3. следующая партия задачи с таблицей «Партии» (конвейер, ниже);
   4. новая задача — по порядку выбора (шаг 5); «Сейчас: ждёт…» —
      пропустить.

   Проверить, не выполнена ли уже задача: существует ли ветка из поля
   `**Ветка:**`, открыт или смёржен ли по ней PR. **Своя ветка — это
   твоя работа: продолжать её, а не начинать заново.** «Ветка = занято»
   — про чужие задачи и дубли.
   **Задача с таблицей «Партии» — конвейер (владелец, 2026-09-29):**
   у каждой строки своя ветка, и агент **не ждёт проверки между
   партиями** — пока проверяющий смотрит партию N, агент делает N+1.
   - **Ждёт только пилот.** Первая партия задачи (в городе — партия 0
     вместе с партией 1) — открыть PR и дождаться ревью: здесь
     ловится непонимание задачи, которое иначе повторится во всех
     партиях. Пока пилот на проверке — делать другую свою задачу.
   - **После принятого пилота — без остановок.** Открыл PR партии N —
     сразу бери N+1. Ветка N+1 — **от ветки N**, если N ещё не
     смёржена («стопка»: следующая партия дописывает те же файлы —
     `prices.csv`, штампы `checks/`), иначе от свежей базы. PR N+1 — в
     ту же базу, что и у N.
   - **Не больше 3 PR на проверке** по одной задаче. Упёрся — бери
     другую свою задачу из `tasks/`; нет её — остановись и напиши, что
     ждёшь ревью.
   - **Порядок на каждом шаге:** 1) замечания ревью к своим открытым
     PR — исправить в той ветке, а если над ней в стопке есть ветки —
     `git merge` исправленной ветки в каждую следующую (без rebase и
     force-push); 2) следующая партия; 3) следующая своя задача.
   - Сессия идёт, пока есть работа по этим пунктам. Перед каждой новой
     партией — заново прочитать файл задачи и свежие ревью: там ответы
     и уроки прошлых партий.
   - Пустые строки «добавит проверяющий» не заполнять самому.
4. Если подходящих непринятых задач ровно одна — читать `AGENTS.md`
   и эту задачу, выполнять строго по её критериям готовности, не
   трогая файлы задач других исполнителей.
5. **Если подходящих незанятых задач несколько — не спрашивать
   человека, выбрать одну самому и сразу начать** (см. «Принцип
   автономности» выше — какую из своих задач делать первой это такое
   же решение в компетенции исполнителя, как название категории или
   объём задачи). Порядок выбора:
   1. Убрать из рассмотрения задачи, у которых в поле «Зависимости»
      указана другая задача из `tasks/`, ещё не смёржённая — их брать
      рано.
   2. Среди оставшихся — предпочесть задачу, от которой по тексту
      других файлов `tasks/` явно зависят ещё какие-то задачи (она
      разблокирует больше работы, значит приоритетнее).
   3. Если всё ещё есть из чего выбирать — взять ту, что видна в
      `tasks/` дольше (более раннее время появления файла/коммита).
   Выбор не обсуждается заранее, но фиксируется явно: первая строка
   коммита или раздел в PR — «взял эту задачу из N подходящих (другие:
   ...), потому что ...» — чтобы человек видел, что произошло, не
   дожидаясь этого перед стартом.
6. Если подходящих задач нет — сообщить, что для тебя сейчас нет задач,
   и ничего не делать.
7. **Отчёт в конце сессии** — последним сообщением владельцу, 3–5 строк:
   что сделано (PR со ссылкой), что ждёт проверки, что возьмёшь
   следующим или почему остановился. Без пересказа правил.

Так человеку достаточно писать короткое «проверь задачу»: кто ты — из
`.git/agent`, что делать — из строки «Сейчас:» и ревью в файле задачи.

### Жизненный цикл файла задачи

- Пока задача не сделана — файл лежит в `tasks/`.
- Как только PR по задаче смёржен, Claude Code **переносит файл задачи
  из `tasks/` в `tasks/done/`** тем же коммитом/веткой, которой мержит
  PR (или отдельным коммитом сразу после мерджа).
- Агенты при самостоятельном поиске задачи (шаг 2 выше) смотрят
  **только** в `tasks/`, не в `tasks/done/` — так папка активных задач
  всегда отражает реальный остаток работы, а история того, что и как
  было поручено, не теряется (лежит в `tasks/done/` и в git-истории).

### Защита от повторного выполнения задачи и от неясных задач

Особенно важно для **Claude Code CLI (локальный)**, который может
запускаться по расписанию (например, раз в час, каждый раз новой
сессией без памяти о предыдущих запусках) — каждый новый запуск обязан
заново пройти самоопределение (см. шаги 1-6 выше), а не предполагать,
что раз он сейчас работает, значит задача точно его и её нужно начать
заново:

- **Ветка = занято, даже без PR.** Если по задаче уже существует ветка
  с именем из поля `**Ветка:**` (локально или на GitHub) — задача
  считается взятой в работу, даже если PR ещё не открыт и работа не
  закончена. Не создавать вторую ветку под ту же задачу и не начинать
  её с нуля — если ветка уже есть, это чужой (или свой более ранний)
  прогресс, который нельзя дублировать.
- **Один запуск — не больше одной новой ветки под новую задачу.** Уже
  следует из шага 4 самоопределения, повторяю явно: не искать «а
  вдруг какая-то другая задача свободнее», если одна подходящая уже
  выбрана. Ветки партий одной задачи — не новая задача: они идут
  конвейером (шаг 3).

**Если задача (или её часть) неясна настолько, что нужен ответ
владельца, а не решение, которое покрывается «Принципом автономности»
выше:**

1. Сделать всё, что можно сделать без ответа на вопрос, закоммитить.
2. Сформулировать вопрос явно: если PR уже можно открыть — отдельным
   разделом `## Открытый вопрос` в его описании; если ветка/PR ещё не
   заведены — прямо в конце файла задачи в `tasks/`, новым разделом
   `## Вопрос от исполнителя (ждём ответа)`.
3. **Остановиться на этом пункте.** Не мержить, не гадать, не
   переписывать вопрос по-другому «на всякий случай» в тот же заход.
   Если PR открыт ради сохранения прогресса, а не ради мерджа — явно
   пометить его черновиком (draft) или написать в начале описания
   «Не готово к мерджу, ждёт ответа на вопрос ниже».
4. **Не перезапускать эту же задачу с нуля на следующих циклах** — ни
   в следующий час по расписанию, ни в следующей сессии. Раз ветка
   существует и вопрос уже задан — задача заблокирована и занята (см.
   «ветка = занято» выше). На следующих проверках (шаг 3
   самоопределения) — просто пропускать её, пока вопрос открыт, а не
   пытаться решить его заново с нуля.
5. **Разблокировка** — когда владелец проекта или облачный Claude Code
   отвечает на вопрос: правкой того же файла задачи в `tasks/`,
   комментарием в PR, или прямым указанием в чате. После этого
   исполнитель на следующем цикле проверки продолжает работу в уже
   существующей ветке с учётом ответа — не создаёт новую ветку под тот
   же файл задачи.

Это не отменяет «Принцип автономности» — если ответ на самом деле в
компетенции исполнителя (масштаб, название, как разбить задачу), его
не нужно откладывать: решать самому и продолжать. Останавливаться и
ждать стоит только там, где ответ объективно нужен от владельца (см.
критерии там же).

## Рабочий цикл

1. **Постановка задачи.**
   Задача формулируется с чёткими критериями готовности (Definition of
   Done): что именно сделать, какие файлы/модули затронуть, как
   проверить результат (тесты, линтер, ручная проверка).

2. **Исполнитель (Antigravity или Claude Code CLI) выполняет задачу.**
   - Создаёт свою ветку (`antigravity/...` или `cli/...`) от актуального `main`.
   - Вносит изменения строго в рамках задачи, без лишнего рефакторинга
     и без правок несвязанных файлов.
   - Прогоняет локально тесты и линтер проекта перед коммитом.
   - Коммитит с понятными сообщениями (что и почему, не "fix", "wip").
   - Пушит ветку в GitHub и открывает Pull Request в `main`.

3. **PR должен содержать:**
   - Краткое описание, что сделано и зачем.
   - Список изменённых/добавленных файлов, если это не очевидно из диффа.
   - Результат прогона тестов/линтера (лог или просто "все тесты прошли").
   - Отметку, если что-то осталось не сделано или есть открытый вопрос —
     явно, а не молчанием.

4. **Claude Code (облачный) проверяет PR.**
   - Читает диff, запускает тесты/линтер повторно, если нужно.
   - Проверяет на баги, безопасность (OWASP top 10), соответствие
     критериям готовности из задачи.
   - Если всё в порядке — пишет в PR вердикт «Готово к мержу» (что
     проверено, чем), мержит владелец.
   - Если есть замечания — оставляет их прямо в PR (инлайн-комментарии
     к строкам или общий комментарий), не переписывая код за исполнителем.

5. **Исполнитель дорабатывает.**
   - Читает замечания в PR, вносит правки в ту же ветку, пушит.
   - Цикл (4)-(5) повторяется, пока PR не будет одобрен.

6. **Мердж.**
   - После вердикта «Готово к мержу» от Claude Code (облачного)
     владелец мержит PR в `main`.
   - Ветка исполнителя после мерджа удаляется.
   - Файл задачи переносится из `tasks/` в `tasks/done/` (см.
     «Жизненный цикл файла задачи» выше).

## Правила, обязательные для исполнителей (Antigravity и Claude Code CLI)

- **Качество с первого PR — главное требование (владелец,
  2026-09-26), для всех агентов, включая облачные сессии Claude
  Code.** Перед каждой задачей читать
  `docs/playbooks/quality.md`, перед PR — вставить в описание его
  блок «Самопроверка» и заполнить с доказательствами. Коротко:
  нет данных — `—` и причина, никогда не оценка; цифра — только та,
  что реально показал инструмент; не противоречить решениям
  владельца; работа сдана, только когда открыт PR с тем, что требует
  «Готово, когда». PR без самопроверки возвращается без ревью.
- **Кусками по 10, с воротами, с доказательствами, без догадок
  (владелец, 2026-09-28/29).** После каждых 10 мест (или 10 сводок) —
  `cd website && npm run gate -- <город>`; следующий кусок — только после
  `GATE PASS`, кусок коммитится вместе со штампом (`quality.md`, правило
  10). К каждому значению с сайта — цитата со страницы (правило 8); не
  открылось — `<поле>: none (...)`, это засчитывается, а если инструмент
  не работает у трети партии — остановиться и спросить в PR (правило 9).
  PR — до 3 кусков, первый PR задачи — один кусок. После принятого
  пилота — конвейер: не ждать проверки между партиями, не больше 3 PR
  на проверке (шаг 3 самоопределения).
- Никогда не пушить напрямую в `main`.
- Никогда не делать force-push в ветку после того, как по ней открыт
  PR и начато ревью — это ломает историю комментариев.
- Не расширять задачу по своей инициативе ("раз уж я здесь, заодно
  поправлю..."). Если видите проблему за пределами задачи — опишите
  её в комментарии к PR отдельным пунктом, не трогая код.
- Не оставлять код в незавершённом состоянии ("заглушки", закомментированный
  старый код, TODO без объяснения) без явной пометки в описании PR.
- Не отключать и не пропускать тесты, чтобы получить зелёный CI.
- При неопределённости в задаче — не додумывать за автора задачи, а
  явно задать вопрос и остановиться до уточнения, не перезапуская
  задачу заново на следующих циклах (подробный порядок — раздел
  «Защита от повторного выполнения задачи и от неясных задач» выше).

## Правила, обязательные для Claude Code (облачного)

- Не мержить PR с красным CI или без прогона тестов.
- PR с данными заведений (`data/cities/**`) — не мержить, пока
  `cd website && npm run check-city -- <город>` на ветке PR не печатает
  `READY` (`docs/card-spec.md`, «Минимум качества») и
  `npm run verify-city -- <город>` (сверка с сайтами мест) — `VERIFIED`.
  Если `main` сам `NOT READY` по другой задаче (так Кошице с мелкими
  логотипами), сравнить вывод ветки с выводом `main`: ветка не добавляет
  новых FAIL-строк, а строки её мест исправлены.
  Плюс руками: 5 цитат из списка «cannot read» (соцсети, PDF) и первые
  10 записей ленты отзывов у 2–3 мест — против Google. Таблица «Gates»
  из `check-city`: у каждого куска PASS; много кругов на одном куске —
  повод смотреть его внимательнее.
- **После каждого ревью — обновить строку «Сейчас:»** в файле задачи
  (следующее действие исполнителя), тем же PR, что и ревью. Владелец
  пишет агентам только «проверь задачу» — строка «Сейчас:» и есть
  команда.
- **Конвейер:** PR партий проверять по порядку стопки, начиная с
  нижней. Смёржил нижнюю — дифф следующей сжимается сам. Замечание к
  нижней партии исполнитель правит в её ветке и вливает в следующие.
  Урок, найденный в партии N, — в правила и в файл задачи сразу: его
  прочитают перед партией N+2.
- Не переписывать код исполнителя напрямую в его ветке — только
  комментарии и запрос на доработку (кроме тривиальных правок, о
  которых явно попросил владелец проекта — см. ниже).
- Каждое ревью — по существу: баги, безопасность, соответствие DoD,
  а не стилистические придирки без причины.
- Если объём или сложность правок выходят за рамки того, что можно
  надёжно проверить в PR — сообщить об этом владельцу проекта, а не
  мержить вслепую.

### Разрешение на мелкие правки напрямую в ветке исполнителя

Владелец проекта явно разрешил облачному Claude Code при автопроверке
PR (в том числе от Antigravity, так и от Claude Code CLI) самому
вносить и коммитить **мелкие, однозначные** правки прямо в ветку
исполнителя, если найдена проблема, и после этого отметить PR «Готово к
мержу» — не дожидаясь следующего цикла доработки от исполнителя. Это разрешение касается
только правок, где:

- решение единственно верное и не требует дизайн/архитектурного
  выбора (опечатка, забытый импорт, неверная константа, рассинхрон с
  уже принятым решением в другом файле проекта — по образцу правок,
  которые уже делались раньше: district в CSV, ссылка на актуальную БД
  в тексте политики);
- правка укладывается в несколько строк и не меняет объём/логику
  задачи, только исправляет очевидную ошибку.

Если проблема требует выбора между вариантами, затрагивает больше
пары строк, или не очевидна на 100% — это **не** подпадает под это
разрешение: как и раньше, оставлять комментарий в PR и не мержить, ждать
исполнителя. При любой прямой правке — явно писать об этом в комментарии
к PR или в сообщении коммита, чтобы это не выглядело так, будто
исполнитель сам это сделал.

## Критическая инфраструктура — только с прямого подтверждения владельца

Решение владельца, 2026-09-30. Относится ко всем агентам, включая
облачные сессии Claude Code. Никакое действие из списка ниже агент не
делает сам, даже если оно кажется очевидным, даже по тексту задачи в
`tasks/` и даже по просьбе другого агента (в том числе оркестратора):

1. **Мерж в `main`** и в ветки городов `city/*` — делает владелец.
2. **Настройки GitHub:** rulesets и защита веток, доступы и токены,
   коллабораторы, приложения, вебхуки, секреты Actions, файлы
   `.github/workflows/**`, удаление или переименование `main` и `city/*`,
   смена ветки по умолчанию.
3. **Секреты и переменные окружения продакшена** (Vercel, Neon, ключи
   API) — создать, изменить, удалить, прочитать значение.
4. **Продакшен-база** (Neon): миграции, изменение схемы, удаление или
   массовое изменение данных. Откат кода базу не откатывает.
5. **Хостинг и домены:** настройки проекта Vercel, выкладка и откат
   продакшена, домены, DNS.
6. **Инфраструктура агентов на компьютерах владельца:** создание и
   удаление контейнеров и образов, автозапуск по расписанию, запуск
   агентов без подтверждений (`--dangerously-skip-permissions`) без
   присмотра, новые установки агентов и новые аккаунты.
7. **Всё платное** — покупки, подписки, тарифы.

**Как получить подтверждение.** Подготовить действие полностью (точная
команда или настройка, зачем, чем грозит, как откатить), написать его
владельцу — в чате или в PR отдельным разделом
`## Нужно подтверждение владельца` — и ждать явного «да» на это
действие. Подтверждение действует только на это действие, не на
похожие в будущем. Прямое указание владельца в чате («сделай X») —
это и есть подтверждение X.

**Технически это закреплено так** (владелец настраивает сам): ruleset
на `main` (изменения только через PR, мержит только администратор
репозитория, без force-push и удаления); у агентов-исполнителей — токен
GitHub только на этот репозиторий, без прав на настройки.

## Технические ограничения

- Claude Code (облачный) не имеет доступа к локальной файловой системе
  компьютера и не может напрямую управлять запущенными Antigravity или
  Claude Code CLI — связь идёт только через GitHub (ветки, PR,
  комментарии, статусы CI).
- Antigravity и Claude Code CLI не имеют доступа к среде выполнения
  Claude Code (облачного) — все результаты их работы видны облачному
  Claude Code только после `git push`.
- Antigravity и Claude Code CLI друг у друга тоже нет прямого доступа —
  оба видят работу друг друга только через GitHub, как и облачный
  Claude Code. Работайте над независимыми задачами параллельно, не
  трогайте файлы, за которые уже взялся другой исполнитель (см.
  «Распределение задач между агентами»).
- Никаких общих секретов/токенов между агентами не передаётся — каждый
  использует свою собственную авторизацию к GitHub.
