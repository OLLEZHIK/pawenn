# Качество с первого раза: стандарт для исполнителей

**Кому:** **все агенты, которые сдают работу через PR**: Antigravity
(все установки), Claude Code CLI и облачные сессии Claude Code
(оркестратор, «дизайнер», CLI). **Обязательно к
прочтению перед каждой задачей** (`AGENTS.md`, «Правила, обязательные
для исполнителей»). Правила §1 и самопроверка §2 — для всех; §5 — для
тех, кто ставит задачи и проверяет PR.

Решение владельца (2026-09-26): **главное требование к исполнителю —
качественный результат с первого PR.** Каждый возврат на доработку —
потерянный день. Этот файл собран из реальных ошибок, которые уже
были; каждая строка — чтобы они не повторились.

## 1. Десять правил, которые нарушать нельзя

1. **Нет данных — пусто и причина. Никогда не оценка.**
   Если источник недоступен или не дал цифру — в клетке `—`, а в
   начале файла / в `notes` — почему (`нет доступа к Keyword Planner`,
   `hours: none (site, fb - not published)`). «Ориентировочно»,
   «примерно», «по опыту», «оценка» в колонке с данными — это
   выдуманные данные, даже с пометкой.
   *Было:* колонка «Planner» заполнена диапазонами «0–10 / 10–100» без
   доступа к Planner (PR #101).
   *Было:* Кошице (PR #144) — ссылки Google Maps с придуманными
   номерами (у 30+ мест номера идут подряд: …19283746184, …185, …186),
   придуманные `google_place_id`, круглые числа оценок, координаты
   «48.745000, 21.258000», адреса страниц магазинов, которых нет (404),
   одна клиника записана трижды под разными именами. Ссылку, ID,
   координаты и оценку **копируют** из Google Maps, а не составляют;
   не открылось — поле пустое и причина в `notes`. `check-city` теперь
   это ловит.

2. **Цифра только такая, какую инструмент реально показал.**
   Не пересчитывать, не «нормировать», не выводить из другой цифры.
   Если Google Trends пишет «Недостаточно данных» — пишем `н/д`, а не
   0 и не число из соседнего запроса. Инструмент, который на такой
   объём не работает (Trends для запросов «район + услуга»), не
   использовать для этого вообще — так и написать.
   *Было:* индексы Trends 97 и 100 для запросов по районам, которые
   Trends не считает (PR #100); индекс «посчитан по базовому термину».
   *Было:* целые группы Trends с индексом 0 у всех запросов (PR #136).
   В сравнении у лидера всегда 100; все нули — это «данных нет», то
   есть `н/д`. Очень маленький индекс рядом с лидером — `<1`, как
   показывает Trends. Над таблицей — с чем сравнивали.

3. **Решения владельца важнее твоих идей.** Перед работой прочитать
   список в §4. Не предлагать то, что уже отклонено (бейджи, фото, …),
   и не противоречить принятому.
   *Было:* «в description, бейджи» в рекомендациях (PR #101), хотя
   бейджей не делаем.

4. **Работа не сдана, пока не открыт PR с полным описанием.**
   Коммит в ветке — это не сдача. PR с таблицей/выводом, которые
   требует раздел «Готово, когда» задачи.
   *Было:* данные по 20 клиникам запушены, PR не открыт.
   *Было ещё раз:* сводки отзывов по 38 местам запушены в
   `mac/review-insights-rest`, PR не открыт — открывал проверяющий (#117).
   Последний шаг любой задачи — **открыть PR**, а не `git push`.

5. **Каждый пункт «Готово, когда» — с доказательством в PR.**
   Не «сделано», а вывод команды, таблица, число, ссылка на файл.

6. **Коды и форматы — только из стандарта.** Категории, коды услуг,
   специальности, языки, формат часов — **только** из списков
   `docs/card-spec.md`. Своё слово вместо кода не придумывать, код
   другой категории не брать; поля `note` и т.п. — строго по их
   назначению.
   *Было:* фиксированная цена («Klinické vyšetrenie: 20 €») записана
   только в `price_from` — сайт показал бы «od 20 €» (PR #129).
   Точная сумма — в оба поля.
   *Было:* коды, которых нет в стандарте (`vaccination_cat`,
   специальности `preventive-care`, `mobile-vet`), цены дрессировки у
   передержки, в `note` — название услуги вместо условия (PR #105).

7. **Не уверен — не угадывай.** Сомневаешься в факте (nonstop или нет,
   тот ли это адрес, та ли услуга в прайсе) — поле пустое, в `notes`
   что нашёл, а вопрос — в описание PR отдельным пунктом. Угаданный
   факт хуже пустого поля: его покажут посетителю как правду.
   *Было:* `appointment_only` («только по записи») у 24 мест Кошице, а
   на сайтах — «можно записаться заранее, записанные идут первыми»
   (PR #144). «Можно записаться» ≠ «только по записи»: факт ставится
   только по прямым словам («len na objednávku»).
   *Было:* в исследовании ключевых слов — «в Варшаве налог на собак
   отменён», «бесплатное чипирование от мэрии» без ссылки (PR #136).
   Утверждение о реальном мире в любом файле — только с источником.

8. **Каждое значение с сайта — с доказательством: страница и дословная
   цитата (владелец, 2026-09-28).** Факт, специальность, язык
   обслуживания, часы, неотложка, цена, то, на чём построено описание, —
   строка в `data/cities/<город>/evidence*.csv`: какое значение, **цитата
   как есть на странице** (копировать, не пересказывать, 10–400
   символов), ссылка на эту страницу, дата. Формат и что именно
   доказывать — `docs/playbooks/add-city.md`, раздел 1.4.
   `check-city` не пропустит место без цитат, `verify-city` открывает
   каждую страницу и ищет на ней цитату. Для сводок отзывов доказательство
   — лента отзывов в самом файле (`review-insights.md`, «Лента»).
   Значения из карточки Google Maps (ссылка, ID, рейтинг, координаты) —
   без цитаты, но только копией (правило 1).
   **Правка старой строки — тоже новые данные (2026-09-29):** переписал
   тексты места — цитата `description`, добавил код — цитата на код.
   `check-city` сравнивает ветку с `main` и требует их, даже если строка
   собрана давно.
   *Было:* Варшава — у 28 клиник «карта, паспорт, аптека» с
   «доказательством» — главной страницей, где этого нет (PR #160);
   сводки отзывов, где у места с двумя критическими отзывами из трёх
   все карточки положительные (PR #182). Цитату, которой нет на
   странице, скрипт находит сразу.

9. **Честный пробел засчитывается. Остановиться — можно (владелец,
   2026-09-28).** Не открылся сайт или Google Maps, нет данных — поле
   пустое, в `notes` — `<поле>: none (<где смотрел, что не открылось>)`.
   `check-city` считает такую строку так же, как значение: до READY
   можно дойти без единой догадки. Если инструмент не работает у трети
   мест партии и больше (Maps в урезанном виде, сайты не отвечают) —
   **не собирать дальше**: открыть PR с тем, что сделано, и описать
   проблему в разделе `## Открытый вопрос`. Сдать меньше мест, чем в
   партии, с объяснением — нормально. Возврат PR бывает за выдумку, не
   за честный пробел.
   *Было:* Кошице (PR #144) — чтобы заполнить поля, ссылки Maps и
   оценки составлены; Варшава (PR #160) — телефоны «+48 501 234 567».

10. **Проверка после каждых 10 — программой, не собой (владелец,
    2026-09-29).** Работа идёт кусками по 10 мест (или 10 сводок
    отзывов). После каждого куска — `cd website && npm run gate --
    <город>`: он проверяет только этот кусок **против источников** (сайт
    отвечает, телефон на сайте, каждая цитата на своей странице, сводка
    сходится со своей лентой) и пишет штамп
    `data/cities/<город>/checks/<кусок>.json`.
    - `GATE PASS` — закоммитить кусок **вместе со штампом** и брать
      следующие 10.
    - `GATE FAIL` — исправить строки из списка, **заново открыв
      источник** (не переписывая по памяти), и запустить снова. На
      третьем круге то, что так и не сошлось с источником, убирается:
      поле пустое, `<поле>: none (что не сошлось)`. Не работает сам
      инструмент — остановиться и спросить (правило 9).
    - Следующий кусок — **только после PASS** предыдущего.
    Штамп хранит отпечаток данных куска и все круги проверки.
    `check-city` не пропустит кусок без штампа PASS или изменённый после
    него, поэтому «проверил» нельзя написать — только запустить.
    *Почему не «перечитай своё»:* та же модель подтверждает то, что сама
    написала. Самопроверки в PR #144, #160 и #186 были отмечены целиком,
    а данные — придуманы.

## 2. Самопроверка перед PR — вставить в описание PR и заполнить

Скопировать блок в описание PR. Каждую строку — отметить и дать
доказательство. Строка, которую нельзя отметить, — не прятать, а
написать почему (это нормально; молчание — нет).

```markdown
## Самопроверка (docs/playbooks/quality.md)
- [ ] Прочитал задачу целиком, `AGENTS.md` и документы, на которые ссылается задача
- [ ] Каждый пункт «Готово, когда» — ниже, с доказательством
- [ ] Нет выдуманных/оценочных данных: где данных нет — `—` и причина
- [ ] Каждая цифра/факт — с источником (URL или инструмент) и датой
- [ ] У каждого значения с сайта — цитата в `evidence*.csv` (правило 8); у сводки отзывов — лента `feed`
- [ ] Где инструмент не сработал — `<поле>: none (...)`, а не значение (правило 9)
- [ ] Кусками по 10, у каждого куска `npm run gate` → `GATE PASS`, штамп в `checks/` закоммичен вместе с куском (правило 10); таблица «Gates» из `check-city` — в PR
- [ ] Нет противоречий с решениями владельца (quality.md §4)
- [ ] Коды и форматы — только из стандарта; где не уверен — пусто, вопрос ниже в PR
- [ ] Автопроверки: <команда> → <вывод целиком или последние строки>
- [ ] Перечитал свой дифф целиком: нет лишних файлов, опечаток в slug, пустых строк CSV
- [ ] Не тронул файлы вне задачи (код сайта, другие города, чужие задачи)
- [ ] Что не сделано и почему: <список или «всё сделано»>

## Готово, когда — доказательства
| Пункт из задачи | Доказательство |
|---|---|
| … | … |
```

## 3. Проверки по типу работы

### Данные о местах (`data/cities/**`)
- `cd website && npm run check-city -- <город>` → `READY` и
  `npm run verify-city -- <город>` → `VERIFIED`, вывод обоих целиком
  в PR. `verify-city` ищет каждую цитату из `evidence*.csv` на её
  странице; страницы, которые скрипт прочесть не может (соцсети, PDF,
  сайты на JavaScript), он перечисляет — проверяющий открывает 5 из них
  руками. Он же проверяет: **закрытые места**, **языки** (без языка
  города), круглосуточность, координаты-заглушки,
  **логотипы тяжелее 200 КБ**, **формат review-insights**, **коды
  специальностей**, **цены** (код из категории места, источник,
  `note` до 40 символов, `partial` с пометкой).
- Цифры в описании PR — из вывода скрипта или подсчёта по файлу, не
  по памяти (*было:* «17 груминг, 14 магазинов» при 10 и 10, PR #105).
- Перед добавлением места — поиск дубля по телефону и адресу среди
  уже существующих (`grep` по `businesses.csv`). Одна фирма с двумя
  разными услугами — две записи, это нормально; одно и то же место
  дважды — нет. **Сайт места ведёт (переадресует) на сайт другого места
  из списка** — это второе название того же салона, а не отдельное место:
  не брать (урок 2026-10-08, New York: «Adonis Pet grooming», сайт
  vdpetspa.com уводил на Dalila's Pet Grooming по тому же адресу, и дубль
  попал на 2-е место рейтинга Queens). Если в `notes` пишешь «website
  redirects to …» — это сигнал дубля, а не пометка.
- Источник фактов — официальный сайт или официальная соцсеть места.
  Каталоги (azet, zzz, oma и т.п.) — только список названий для поиска.
- Логотип — PNG/SVG/WebP, до 200 КБ, достаточно 512 px по длинной
  стороне. Большой файл — уменьшить перед коммитом.
- Все правила полей — `docs/card-spec.md`, раздел «Проверка перед PR».

### Исследования (ключевые слова, конкуренты, рынок)
- В начале файла: дата, **какие источники были доступны и какие нет**.
- Разделять **факт** (что показал инструмент) и **вывод** (что
  предлагаешь). Вывод можно делать, даже когда цифр нет, — но он
  помечен как вывод, а не выдаётся за данные.
- Ноль/«н/д»/«нет данных» — это результат, его записывают как есть.

### Тексты и контент (описания, сводки отзывов, переводы)
- Оба языка по смыслу одинаковые; местный язык — живой, не калька.
- Никаких цитат, имён и историй от лица клиентов; только обобщение
  («Viacerí zákazníci…»). Тема сводки — от 3 разных авторов.
- Длины и количество — как в задаче (например, карточка 250–450
  символов); `check-city` проверяет формат review-insights.
- Перевод — тот же смысл, без добавлений и в том же лице: сайт
  говорит о месте в третьем лице («miejsce podaje…»), не «мы
  предлагаем». *Было:* в ответах FAQ фактов — «bezpłatny odbiór»,
  «certyfikowany kurs», «oferujemy» там, где место заявило только сам
  факт (PR #139).
- Числа с существительным — формами из `plural()`, никогда не
  приклеивать окончание к подписи (`${singular}y`): в польском после 5
  нужен родительный падеж, которого у подписей нет. Считать через слово
  с готовыми формами («miejsce / miejsca / miejsc»), как словацкий
  считает «podnik». *Было:* «lecznica weterynaryjnay» (PR #139).

| «Коротко о месте» (`facts`) — только коды из списка категории и только то, что место само пишет; нет кода = «не указано» | `docs/card-spec.md` §9 |
| Единственная cookie сайта — `pawenn_lang` | `docs/legal/privacy-policy.md` |

## 5. Для тех, кто ставит задачи и проверяет PR

**Стандарт пополняет проверяющий.** Каждая новая ошибка, найденная в
PR (возврат на доработку или правка при мердже):
1. пример в §1 (строка «*Было:* …, PR #N») у подходящего правила или
   новое правило;
2. если ошибку может поймать скрипт — проверка в `check-city` (или
   другом скрипте) в том же или следующем PR;
3. если ошибка из-за неясной постановки — правка шаблона задачи или
   плейбука.

Так одна и та же ошибка не повторяется: второй раз её ловит скрипт или
правило, которое исполнитель читает перед работой.

**Цели покрытия не должны толкать к выдумке.** Если `check-city` требует
долю мест с полем, честная пометка «<поле>: none (где смотрел)» должна
засчитываться так же, как значение (ссылка Maps, факты — PR #147, #151).
Иначе агент без данных может сдать работу, только заполнив поле чем
угодно.

**Автоматическая проверка сайтов** (обход скриптом): обычный заголовок
браузера (`User-Agent` Chrome), не короткий «Mozilla/5.0» — часть хостингов
на него отвечает «Access Forbidden», и пустой ответ выглядит как «на сайте
ничего нет» (PR #151). Смотреть не только главную: прайсы и условия часто
на внутренних страницах и в PDF.

**Сразу, а не потом (владелец, 2026-09-27).** Ошибку, найденную при
ревью, вносить в инструкцию (`add-city.md`, `card-spec.md`, плейбук
работы) и, если можно, в `check-city` в тот же день — а не только в
комментарий к PR или файл задачи. Цель — добавление городов без
ручной доводки.

**Задачи.**

Задача, после которой исполнитель ошибается, — наполовину ошибка
постановки. Шаблон — `docs/playbooks/task-template.md`. Каждая новая
задача в `tasks/`:

- **маленькая (владелец, 2026-09-28/29):** работа кусками по 10 мест
  (или 10 сводок) с `npm run gate` после каждого (правило 10); PR — до 3
  кусков, первый PR задачи — 1 кусок (пилот: его ревью ловит
  непонимание задачи, которое скрипт не видит). Больше — таблица
  «Партии», по PR на строку (`add-city.md`, «Партии»). Большая партия к концу превращается в
  шаблон и выдумку (все описания Кошице и Варшавы, 63 сводки Варшавы
  «за час»); маленькая проверяется, пока ошибку дёшево исправить;
- требует **доказательства** к каждому значению (правило 8) и прямо
  **разрешает честный пробел и остановку** (правило 9) — одной фразой в
  разделе «Если инструмент не работает»;

- ссылается на этот файл («Перед PR — самопроверка из
  `docs/playbooks/quality.md`»);
- в «Готово, когда» — только **проверяемые** пункты (команда, файл,
  таблица, число), без «хорошо», «качественно»;
- называет **формат результата** (файл, колонки, пример строки);
- перечисляет **чего не делать**, особенно известные ошибки этого типа
  работы (§1);
- говорит, что делать, если инструмент/источник недоступен (пропустить
  шаг и написать об этом — а не заменять оценкой);
- не ставит работу, полезную только одному городу (Братислава —
  образец для шаблонов, `docs/growth-strategy.md` §0): результат
  должен переноситься на любой город и язык;
- если правило можно проверить скриптом — добавить проверку в
  `check-city` (или другой скрипт), а не только написать словами.
- **Не добавлять требований, которые не проверены (владелец,
  2026-09-27).** Если способ уже сработал на прошлой задаче того же
  типа, повторить его, а не придумывать новое условие. *Было:* в задачу
  по отзывам Кошице дописано «нужен вход в Google», хотя Братиславу
  (PR #121) собрали без входа, и исполнитель остановился, попросив
  владельца войти. Перед новым требованием: сработало ли прошлый раз
  без него? Если да — не писать.
